# RK4 compilation investigation

**Goal:** Reproduce and localize whole-step numerical drift before any wider
compilation or production integration.

**Architecture:** An isolated experimental simulator compiles the existing bound
`RaptorSimulator.step` with `backend="inductor", fullgraph=True`. The original
step remains the single source of RK4 equations and operation order. Actor,
observation, termination/compaction, loss, Time Decay, grouped backward, clipping
and Adam stay outside this boundary.

**Execution:** Same agent/thread; no delegation, training or checkpoint rewrite.
Use PyTorch 2.10 to match the repository and historical GPU version.

## Fixed checks

Use existing short-rotation FP32 limits: state/cost `rtol=1e-6, atol=1e-6`,
derivatives `rtol=1e-5, atol=1e-6`. FP64 uses the historical whole-step limits
`rtol=3e-9, atol=2e-10`. Do not change these to obtain a pass. Historical H500
raw thresholds, absent from the current checkout, must not be invented.

Keep `tests/core_contract.json`, production Python kernels and calibration
unchanged during this investigation. A passing small fixture is not approval
for production, learned performance, deployment or whole-rollout compilation.

## Causal result

Default CUDA 2.10 Inductor fails the unchanged H500 gates. Value/VJP
interventions place the dominant error in forward drift; exact sum-order
oracles identify an independent torque-reduction source alongside FMA.
Restoring native sum/cross/norm/bmm boundaries and precision/division controls
makes the same 2048-scene H500 trajectories, grouped gradients, clipping and
shadow Adam bitwise equal. This is a diagnostic sufficient combination, not a
production backend, a minimality proof or a speed claim. See gpu_efficiency.md
and reports/rk4_compile_20261019/ for evidence.
